# SQLSpec Migrations

This directory contains database migration files.

## File Format

Migration files use SQLFileLoader's named query syntax with versioned names:

```sql
-- name: migrate-20251011120000-up
CREATE TABLE example (
    id NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY PRIMARY KEY,
    name VARCHAR2(255) NOT NULL
);

-- name: migrate-20251011120000-down
BEGIN
    EXECUTE IMMEDIATE 'DROP TABLE example PURGE';
EXCEPTION
    WHEN OTHERS THEN NULL;
END;
```

## Naming Conventions

### File Names

Format: `{version}_{description}.sql`

- Version: Hybrid sequential (`0001` baseline) or 14-digit UTC timestamp (`YYYYMMDDHHmmss`)
- Description: Brief description using underscores
- Examples: `0001_cymball_coffee_products.sql`, `20251011120000_create_users_table.sql`

### Query Names

- Upgrade: `migrate-{version}-up`
- Downgrade: `migrate-{version}-down`

## Version Format

Migrations use SQLSpec's **hybrid sequential + timestamp versioning** tracked in the `migrations` table:

- **Baseline revision**: 4-digit sequential version (`0001_cymball_coffee_products.sql`)
- **Subsequent revisions**: 14-digit UTC timestamp (`YYYYMMDDHHmmss`, e.g., `20251011120000`)
- **Benefits**: Preserves a deterministic baseline revision while eliminating merge conflicts when multiple developers create new migrations concurrently

### Creating Migrations

Use the local SQLSpec management entrypoint to generate timestamped migrations:

```bash
uv run python manage.py database create-migration -m "add user table"
# Creates: 20251011120000_add_user_table.sql
```

The timestamp is automatically generated in UTC timezone.

## Migration Execution

Migrations are applied in version order (sequential baseline revisions first, followed by chronological UTC timestamps) and recorded in the `migrations` tracking table alongside execution metadata so out-of-order branch merges are tracked cleanly.

During onboarding and deployment, `uv run coffee upgrade` runs SQLSpec schema
and extension migrations (`app_session` plus the `litestar-queues` tables
`queue_task`, `queue_task_event_history`, `queue_maintenance`, and
`queue_task_reservation` configured by `DatabaseSettings.create_config()` in
`src/app/lib/settings/_database.py`; `uv run python manage.py database upgrade`
runs those schema and extension migrations without loading fixtures) and
upserts the committed fixture datasets from `src/app/db/fixtures/` via
`FixtureLoader` (`load_fixtures()` in `src/app/db/utils.py`), resynchronizing
identity sequences after loading.

## Current Baseline Schema (0001)

The baseline Oracle AI Database 26ai schema in
`src/app/db/migrations/0001_cymball_coffee_products.sql` includes:

- `product` table (`INMEMORY PRIORITY HIGH`) with `BOOLEAN` `in_stock` flag, `JSON` metadata, and `VECTOR(3072, FLOAT32)` embeddings produced by `gemini-embedding-2` (`130` committed fixture rows).
- `store` table for retail location data with `JSON`-encoded business hours (`17` committed fixture rows).
- `store_product_inventory` table for curated store-level product availability (`1,700` committed fixture rows).
- `response_cache`, `embedding_cache` (`UNIQUE (text_hash, model)` with `VECTOR(3072, FLOAT32)` cached query embeddings), and `search_metric` support tables.
- `agent_session` and `agent_event` tables for the native `AgentRuntime`.
- `chat_route` (`INMEMORY PRIORITY HIGH`) table with `VECTOR(3072, FLOAT32)` route exemplar embeddings (`25` committed exemplars across `5` route labels).
- HNSW vector indexes (`ORGANIZATION INMEMORY NEIGHBOR GRAPH`, `DISTANCE COSINE`, `WITH TARGET ACCURACY 95`, `PARAMETERS (TYPE HNSW, NEIGHBORS 40, EFCONSTRUCTION 500)`) on `product` (`product_embedding_idx`) and `chat_route` (`chat_route_embedding_idx`).
- Oracle Text `MULTI_COLUMN_DATASTORE` preferences (`product_search_ds`, `store_search_ds`, `route_search_ds`) and `CTXSYS.CONTEXT` indexes (`product_hybrid_ctx_idx`, `store_hybrid_ctx_idx`, `chat_route_ctx_idx`) with `SYNC (ON COMMIT)`.

## Schema Annotations

The baseline DDL demonstrates Oracle AI Database 26ai schema annotations
inline in the existing `CREATE TABLE`, column definition, and supported
`CREATE INDEX` statements. `COMMENT ON` statements remain in place for
compatibility with older tooling; annotations carry richer application metadata
such as embedding model, dimensions, distance metric, cache role, and the
privacy boundary for store coordinates.

Inspect the applied metadata through Oracle's annotation dictionary views:

```sql
SELECT object_name,
       object_type,
       column_name,
       annotation_name,
       annotation_value
FROM user_annotations_usage
WHERE object_name IN (
    'PRODUCT',
    'STORE',
    'STORE_PRODUCT_INVENTORY',
    'EMBEDDING_CACHE',
    'PRODUCT_IN_STOCK_IDX'
)
ORDER BY object_name, column_name, annotation_name;
```

## Vector Memory Pool

Oracle AI Database 26ai requires a non-zero `vector_memory_size` allocation
before HNSW `INMEMORY NEIGHBOR GRAPH` indexes can be built. Without it,
`CREATE VECTOR INDEX ... ORGANIZATION INMEMORY NEIGHBOR GRAPH` fails with
`ORA-51962`.

- **Autonomous AI Database Free 26ai (default `make start-infra`) and Cloud Autonomous AI Database**: The default local development container (`container-registry.oracle.com/database/adb-free:latest-26ai`, container `cymbal-adb-free`, connected via the `.envs/tns` mTLS wallet for `myatp_low` on TLS port `1522`) and managed Autonomous AI Database instances allocate vector memory automatically with no manual SPFILE change required.
- **Oracle AI Database Free (`ORACLE_CONTAINER_FLAVOR=free` / `make test-integration`)**: On `gvenzl/oracle-free:latest` (`:1521/freepdb1`), `sga_max_size` and `sga_target` are capped (`ORA-56752` if raised), so the vector pool fits inside the existing ~1.5 GB SGA. The container lifecycle mounts `tools/oracle/on_init/00_configure_vector_memory.sql` into `/container-entrypoint-initdb.d` (setting `vector_memory_size = 512M SCOPE=SPFILE` and restarting the instance once on initial creation) and `tools/oracle/on_startup/00_verify_vector_memory.sql` into `/container-entrypoint-startdb.d` (verifying `V$SGAINFO` on every startup). `512M` comfortably holds the `130` product vectors and `25` route exemplar vectors at `3072` dimensions.
- **Self-managed Oracle Free, Standard, or Enterprise Edition**: Configure the pool once on the SPFILE as `SYSDBA` and restart the instance. Keep `512M` on Free Edition (`ORA-56752` applies if SGA targets are increased), or scale `sga_max_size` / `sga_target` (for example `6G`) and `vector_memory_size` (for example `4G`) on Standard and Enterprise Edition:

```sql
ALTER SYSTEM SET vector_memory_size = 512M SCOPE=SPFILE;
SHUTDOWN IMMEDIATE;
STARTUP;
```

Verify the pool is allocated:

```sql
SELECT NAME, BYTES FROM V$SGAINFO WHERE NAME LIKE '%Vector%';
```

A non-zero `Vector Memory` row confirms the pool is live. Scale `vector_memory_size` higher on Standard or Enterprise Edition if large `uv run coffee bulk-embed` datasets report `ORA-51963` (pool exhausted); Oracle's rough HNSW memory estimate is `1.3 * rows * dim * element_bytes`, and `DBMS_VECTOR.INDEX_VECTOR_MEMORY_ADVISOR` provides exact sizing.
