# Architecture Patterns

<!-- truth: start -->
- Litestar app setup stays thin: `src/app/server/` wires plugins, middleware, routes, and templates; domain packages own behavior.
- Domain packages use `controllers/`, `services/`, and `schemas/` subpackages. Cross-domain imports go through package exports, not deep private modules.
- Dishka has exactly three user providers in `src/app/ioc.py`: `LitestarPersistenceProvider`, `IntegrationsProvider`, and `DomainServiceProvider`.
- `LitestarPersistenceProvider` owns APP-scoped `OracleAsyncConfig` and REQUEST-scoped `OracleAsyncDriver`.
- `IntegrationsProvider` owns APP-scoped external integrations: GenAI client, GeminiModelClient, AgentRuntime, SpecTree, OracleSessionStore, and OracleEventStore.
- `DomainServiceProvider` owns REQUEST-scoped services: products, stores, cache, metrics, tools, Vertex AI, vector-search orchestration, AgentOrchestrationService, and AgentStreamService.
- SQL lives in `src/app/db/sql/*.sql` as named queries. Domain services call `db_manager.get_sql("name")`; inline service SQL is rejected by tests.
- List endpoints use `create_filter_dependencies` in controllers and `list_with_count(*filters)` in services for pagination/filter wiring.
- Product vectors and embedding-cache vectors are `VECTOR(3072, FLOAT32)` values generated by `gemini-embedding-2`.
- Oracle feature-demo metadata belongs inline in the baseline DDL when the branch is still curating the reference schema. Keep `COMMENT ON` statements for compatibility and add 26ai `ANNOTATIONS(...)` on documented table, column, and normal-index surfaces; do not create follow-up migrations or separate `ALTER ... ANNOTATIONS(...)` statements just because local SQL parsers lag Oracle syntax.
- AI conversation and session persistence uses SQLSpec named queries in `ai-runtime.sql` backing `OracleSessionStore` and `OracleEventStore` (`AGENT_SESSION`, `AGENT_EVENT`). Litestar browser sessions use `app_session`.
- Chat uses native `AgentOrchestrationService` with classifier-first intent routing (`FlashLiteIntentClassifier`). Re-entrant `AgentRuntime.execute_turn()` executes specialist turns with prompt fencing (`<<<BEGIN_SYSTEM_INSTRUCTION>>>`), parallel tool dispatch (`execute_parallel()`), and turn/step limits.
- Agent tools are closure-bound per request with `CallContext`, receiving request-scoped services through `ctx.state` rather than global singletons.
- `/api/chat/stream` is an SSE endpoint adapted via `AgentStreamService`. It streams structured event frames (`session`, `tool_call`, `tool_end`, `delta`, `ping`, `final`), emitting keep-alive pings every 5 seconds to prevent connection drops.
- Chat page history is hydrated via `AgentOrchestrationService.get_display_history()`, returning `ChatMessage` instances with `.source` (`human` or `ai`) and `.message`.
- The chat sidebar clear button deletes the session/events in `OracleSessionStore`/`OracleEventStore` and clears only the Litestar chat session bridge keys. It does not clear menu data, metrics, response cache, or embedding cache.
- Multi-protocol machine endpoints: `LitestarMCP` mounts at `POST /mcp` with skill definitions and route-annotated tools (`mcp_tool="search_coffee_products"`); `LitestarA2A` mounts at `POST /a2a` with JSON-RPC agent execution (`CoffeeAgentExecutor`) and public discovery at `GET /.well-known/agent-card.json`.
- Store/location/inventory work stays in the products domain: seed coordinates, Dallas, and curated inventory; route store answers from service facts.
- Store selectors and inventory UI must be driven by `StoreService` and fixture data. Do not hardcode a few store IDs in Jinja as "presets"; that silently narrows the demo to those locations and drifts from the seeded store list.
- Store-aware product RAG must vary or bypass response-cache reads whenever safe location/store context is present, so one store's inventory answer is not reused for another store.
- Maps URLs are the no-key baseline. Browser coordinates are opt-in and request-scoped; embeds require a separate restricted Maps Embed key.
- Frontend pages are HTMX + Jinja + Tailwind v4 + vanilla JavaScript/ApexCharts through `litestar-vite` template mode, not a standalone SPA.
- `src/resources/` is the Vite/npm project root. Keep `package.json`, `package-lock.json`, `tsconfig.json`, `vite.config.ts`, `public/`, generated bridge files, and `node_modules/` there; Python `ViteConfig.paths.root` must point at the same directory.
- Explore-only educational calculators stay client-only in `src/resources/*.js` and wire to Jinja markup through `data-*` attributes. Keep this as vanilla Vite-bundled JavaScript.
- Vector footprint estimates use raw bytes by format (`N * d * 8` for FLOAT64, `N * d * 4` for FLOAT32, `N * d` for INT8, `N * ceil(d / 8)` for BINARY), and Oracle's rough HNSW Vector Pool estimate of `1.3 * N * d * element_size`. Use `DBMS_VECTOR.INDEX_VECTOR_MEMORY_ADVISOR` for exact HNSW/IVF sizing; do not model IVF or HNSW neighbors with invented client-side overhead formulas.
- EXPLAIN PLAN uses two named SQL calls: one `EXPLAIN PLAN FOR ...` and one `DBMS_XPLAN.DISPLAY()` read.
- `coffee` is the app CLI. Keep `bulk-embed`, `export-fixtures`, `load-fixtures`, `clear-cache`, `model-info`, and `run` visible there.
- Keep public CLI modules mostly declarative. Large workflows belong in focused private `app.cli._helpers` modules; small command-local helpers can live in `commands.py`. Do not add compatibility shim or facade modules.
- `sanitize_for_json` camel-cases msgspec Struct keys for wire encoding. In the chat domain (like `ADKRunner` and grounding formatting helpers), check both snake_case and camelCase keys using `_get_field(row, snake_name)` to remain resilient to case conversion differences between unit test mocks and runtime database responses.
- Product availability lookups (`PRODUCT_AVAILABILITY`) resolve product names via exact match first, falling back to pronoun resolution from `last_products` in session history, and finally using Vertex AI vector search to resolve partial/imprecise product names (e.g. 'Gemini' -> 'Gemini Rush') before checking store inventory.
- ORDS Stateless Deployment on Cloud Run: Deploy ORDS on Cloud Run stateless, peered via Direct VPC, utilizing Secret Manager for the database system password (`DATABASE_SYSTEM_PASSWORD`) to enable automatic schema registration/validation on container boot.
- Oracle CDN for APEX Assets: Set `IMAGE_PREFIX` to Oracle's public APEX CDN (`https://apex.oracle.com/i/` or version-specific URL) via database script. This keeps the ORDS container stateless and avoids mounting static asset directories or using Cloud Storage FUSE.
- Image Re-hosting for Private Deployments: When deploying to Cloud Run in restricted environments where external registry authentication is unavailable or unreliable at deployment time, re-host official images in GCP Artifact Registry.
- AutoREST Table Enablement: Utilize Oracle ORDS `AutoREST` capability to expose database tables (e.g., `PRODUCTS`) as REST endpoints directly via SQLSpec migrations or startup scripts using simple PL/SQL calls (`ORDS.enable_object`), providing a zero-code private data access path.
- Naming a query parameter argument `query` in a Litestar controller action causes Litestar to pass the entire query parameters `MultiDict` to it. Use a different Python argument name (e.g., `search_query`) and map it explicitly using `QueryParameter(name="query")` to avoid this.
- Domain autowiring: Use `litestar-autowire[dishka]` (`AutowirePlugin(AutowireConfig(domain_packages=["app.domain"], integrations=["dishka"]))`) for declarative controller discovery and automatic `DishkaRouter` resolution; avoid custom domain scanner plugins. Clear test cache with `clear_autowire_cache()`.
- Background workers: Use `litestar-queues` 0.12.0 with separate persistence, placement, wakeups, and task events. Adopt unified CLI runners (`--worker-only`), dedicated queue maintenance CLI (`coffee queue ...`), bounded maintenance loops, multi-role config factories (`web`, `consumer`, `cli`), and request-scoped Dishka DI per task invocation via `task_dependency_provider`.
- Oracle Transactional Event Queues (`txeventq`): Configure native Oracle 26ai transactional queuing in SQLSpec via `sqlspec.adapters.oracledb.events.OracleAsyncTxEventQEventBackend` using `extension_config={"events": {"backend": "txeventq", "aq_queue": "..."}}`. Enqueues participate atomically in database transactions and bridge to Litestar Channels via `SQLSpecChannelsBackend`.
- Stateless Security & MCP: Separate Authentication (`auth=`, `SecureController`, `PublicController`) from Authorization (`guards=[...]`). Use the Authorization Snapshot Pattern (single async resolver generating an immutable snapshot for zero-DB synchronous guards) and expose route-marked endpoints (`mcp_tool=`, `mcp_resource=`) via stateless POST `/mcp` with `litestar-mcp`.
- HTMX 2.x & `litestar-htmx`: Import strictly from `litestar_htmx`, never deprecated `litestar.plugins.htmx`. Reserve `HTMXTemplate` for partial fragments setting HTMX headers (`push_url`, `re_swap`, etc.); full pages return standard `Template`. Use `hx-ext="ignore:<extension>"` to break inherited extension parsing on subtrees.
